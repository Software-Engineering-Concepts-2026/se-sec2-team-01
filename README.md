## 💡 เกี่ยวกับโปรเจกต์

หลายคนรู้ว่าตัวเอง "นอนไม่พอ" แต่ไม่รู้ว่านอนไปเท่าไหร่จริง ๆ นอนมีคุณภาพแค่ไหน และอะไรที่ทำให้คืนนั้นแย่ลง **Good Night** จึงเป็นเว็บแอปที่:

1. **บันทึก** เวลานอนได้ง่าย ทั้งแบบกดจับเวลาตอนเข้านอน/ตื่น และกรอกย้อนหลัง
2. **วิเคราะห์** ระยะเวลาหลับจริง ประสิทธิภาพการนอน และ Sleep Score พร้อมกราฟรายวัน/รายเดือน
3. **แนะนำ** สิ่งที่ควรปรับ จากข้อมูลของผู้ใช้เอง เช่น เวลาเข้านอนที่ทำให้นอนได้ดีที่สุด หรือปัจจัย (คาเฟอีน มือถือ ความเครียด ฯลฯ) ที่สัมพันธ์กับการตื่นมาไม่สดชื่น

> ⚠️ Good Night ให้คำแนะนำทั่วไปจากข้อมูลที่ผู้ใช้บันทึกเท่านั้น **ไม่ใช่การวินิจฉัยทางการแพทย์**

## 📖 วิธีใช้งาน

เปิดเว็บที่ 👉 **https://good-night-webapp.vercel.app/**

### 1. สมัครสมาชิก
1. กด **สมัครใช้งาน** แล้วกรอกข้อมูล (รหัสผ่านอย่างน้อย 8 ตัวอักษร)
2. อ่านและติ๊กยอมรับ **นโยบายความเป็นส่วนตัว** — ปุ่ม "สร้างบัญชี" จะกดได้เมื่อกรอกครบแล้วเท่านั้น

### 2. ตั้งเป้าหมาย (ครั้งแรก)
1. กำหนด **ชั่วโมงนอนต่อคืน** — พิมพ์ชั่วโมง/นาทีได้เลย หรือกด `−` / `+`
2. ไม่แน่ใจว่าควรนอนเท่าไหร่? กด **"ไม่รู้ว่าควรนอนกี่ชั่วโมง?"** แล้วใส่อายุ ระบบจะแสดงช่วงที่แนะนำ
3. ตั้ง **เวลาเข้านอน** (ไม่บังคับ — ปล่อยว่างไว้ได้ ระบบจะแนะนำให้ภายหลัง)
4. กด **เริ่มใช้งาน** — แก้ไขได้ทุกเมื่อที่ ตั้งค่า › เป้าหมาย

### 3. บันทึกการนอน (เลือกได้ 2 วิธี)

| วิธี | ขั้นตอน |
|---|---|
| ⏱️ **จับเวลา** | กด **เริ่มนอน** ก่อนนอน → ตื่นมากด **ตื่นแล้ว** → ระบบกรอกเวลาให้ → ตอบคำถามสั้น ๆ → **บันทึกข้อมูล** |
| ✍️ **กรอกเวลา** | ไปที่ **บันทึกการนอน › กรอกเวลา** → ใส่วันที่/เวลาเข้านอนและตื่น → ตอบคำถาม → **บันทึกข้อมูล** |

คำถามในแบบบันทึก:
- ใช้เวลานานแค่ไหนกว่าจะหลับ · ตื่นกลางดึกหรือไม่
- ตื่นมาสดชื่นแค่ไหน (1–5) · รู้สึกอย่างไร (มีพลัง, สงบ, เฉย ๆ, ยังเพลีย, หงุดหงิด, กังวล)
- ปัจจัยเมื่อคืน (คาเฟอีน, เล่นมือถือ, ออกกำลังกาย, เครียด, มื้อดึก, แอลกอฮอล์)
- บันทึกเพิ่มเติม

> 💡 ด้านขวาของฟอร์มจะสรุป **ระยะเวลาหลับจริง / ประสิทธิภาพ / เวลาบนเตียง / เวลาที่เสียไป** ให้ดูทันทีก่อนกดบันทึก

### 4. ดูผลและแนวโน้ม
- **หน้าหลัก** — สรุปคืนล่าสุด, Sleep Score, กราฟ 7 วัน, การ์ดแนะนำเวลาเข้านอน
- **สถิติ** — สลับ "7 วันล่าสุด / รายเดือน", ดูปัจจัยที่สัมพันธ์กับความสดชื่น (กด "ดูบันทึกที่ใช้คำนวณ" เพื่อดูว่าคิดจากคืนไหน)
- **คำแนะนำ** — เปิดใช้เมื่อบันทึกครบ 7 คืน
- **ประวัติ** — แตะรายการเพื่อดูรายละเอียด/แก้ไข/ลบ, กด **เลือก** เพื่อลบหลายรายการ, กด **ส่งออก CSV** เพื่อสำรองข้อมูล (เปิดใน Excel / Google Sheets ได้)

### 5. ตั้งค่า
| เมนู | ทำอะไรได้ |
|---|---|
| โปรไฟล์ | กด ✎ ที่รูปเพื่อเปลี่ยนรูป, กด ✎ หลังชื่อเพื่อแก้ชื่อ |
| เป้าหมาย | แก้ชั่วโมงนอนและเวลาเข้านอน |
| นโยบายความเป็นส่วนตัว | อ่านนโยบาย และถอนความยินยอม |
| ออกจากระบบ | — |
| ลบบัญชีผู้ใช้ | ลบบัญชีและบันทึกทั้งหมด (ย้อนกลับไม่ได้) |

## 🧮 การคำนวณและตรรกะของระบบ

| ค่า | สูตร / กติกา |
|---|---|
| **เวลาบนเตียง** | เวลาตื่น − เวลาเข้านอน (รองรับการนอนข้ามเที่ยงคืน; ถ้าจับเวลาจะใช้ timestamp จริง) |
| **หลับจริง** | เวลาบนเตียง − เวลากว่าจะหลับ − เวลาตื่นกลางดึก |
| **ประสิทธิภาพการนอน** | หลับจริง ÷ เวลาบนเตียง × 100 · เกณฑ์ดี **≥ 85%** |
| **นอนน้อยมาก** | หลับจริง < 4 ชม. หรือ < ครึ่งหนึ่งของเป้า → ไม่แสดงประสิทธิภาพเป็น "ผ่านเกณฑ์" แม้ตัวเลขจะสูง |
| **Sleep Score (0–100)** | 50% ระยะเวลาเทียบเป้า + 30% ประสิทธิภาพ + 20% ความสดชื่น (ถ้าไม่ได้ให้คะแนนความสดชื่น จะคิดจากสองส่วนแรก) · ≥ 85 ดีมาก, ≥ 70 ดี, ≥ 50 พอใช้ |
| **7 วันล่าสุด** | 7 วันตามปฏิทินจริง วันที่ไม่ได้บันทึกแสดงเป็นช่องว่างในกราฟ |
| **เข้านอนตรงเป้า** | คลาดเคลื่อนไม่เกิน ±30 นาที |
| **แนะนำเวลาเข้านอน** | ต้องมี ≥ 7 คืน · หาช่วง 30 นาทีที่ Sleep Score เฉลี่ยสูงสุด (≥ 2 คืน และดีกว่าค่าเฉลี่ยรวม ≥ 3 คะแนน) |
| **สรุปผลเป้าหมาย** | ครบ 7 วันหลังตั้งเป้า และมีบันทึก ≥ 3 คืน → เทียบ Sleep Score ก่อน/หลัง |
| **วิเคราะห์ปัจจัย** | ต้องมีคืนที่ให้คะแนนความสดชื่น ≥ 3 คืนทั้งกลุ่ม "มี" และ "ไม่มี" ปัจจัย |

## 🎨 Front End

แอปฝั่งผู้ใช้เป็น **Single Page Application แบบไฟล์เดียว** (HTML + CSS + JS อยู่ในไฟล์เดียว) ไม่มี build step และไม่มี dependency ภายนอกตอนรัน — เปิดเร็ว ใช้งานออฟไลน์ได้ และ deploy เป็น static site ได้ทันที

### โครงสร้างโค้ด

| โมดูล | หน้าที่ |
|---|---|
| `window.GN` — **Core logic** | คำนวณการนอน, Sleep Score, ช่วงวันที่, session จับเวลา, เป้าหมาย, คำแนะนำ, วิเคราะห์ปัจจัย, CSV — ไม่ยุ่งกับ DOM จึงทดสอบใน Node ได้ |
| `window.GN_CONFIG` | ค่าตั้งค่าการเชื่อมต่อ Back End |
| `window.GNCloud` — **Supabase client** | สมัคร/เข้าสู่ระบบ/รีเซ็ตรหัสผ่าน และอ่าน-เขียนข้อมูลผ่าน REST ด้วย `fetch` |
| `window.GNBcrypt` | แฮชรหัสผ่านสำหรับโหมดใช้งานในเครื่อง |
| **App UI** | Routing (hash-based), การ render แต่ละหน้า, event handling, คิวซิงก์ข้อมูล |

### หน้าจอ

`สมัคร/เข้าสู่ระบบ` → `ขอความยินยอม` → `ตั้งเป้าหมาย` → `หน้าหลัก` · `บันทึกการนอน` · `ประวัติ` · `รายละเอียดรายคืน` · `สถิติ` · `คำแนะนำ` · `ตั้งค่า`

### Design System

- **ธีมมืดโทนม่วงกลางคืน** สบายตาเวลาเปิดก่อนนอน/ตอนเพิ่งตื่น

| Token | สี | ใช้กับ |
|---|---|---|
| `--bg` | `#17142B` | พื้นหลัง |
| `--surface` | `#231F3D` | การ์ด, dialog |
| `--primary` | `#6D5BD0` | ปุ่มหลัก, แท่งกราฟ |
| `--accent` | `#B8ACFF` | ไอคอน, ลิงก์ |
| `--good` | `#6EE7B7` | ผ่านเกณฑ์ |
| `--warn` | `#FCA5A5` | ต่ำกว่าเกณฑ์ / คำเตือน |
| `--star` | `#FCD34D` | ความสดชื่น |

- Responsive: แถบเมนูซ้ายบนจอ ≥ 900px และแถบเมนูล่างบนมือถือ
- Accessibility: ปุ่มกดได้ขนาดอย่างน้อย 44–48px, `aria-*` บนตัวเลือกทั้งหมด, focus ring ชัดเจน, รองรับ `prefers-reduced-motion`
- กราฟสร้างด้วย HTML/CSS (ไม่ใช้ไลบรารีกราฟ)

> รายละเอียด design system และตรรกะทั้งหมดอยู่ใน `good-night-design-and-logic.md`

## 🗄️ Back End

### Supabase
| บริการ | ใช้ทำอะไร |
|---|---|
| **Auth** | สมัครด้วยอีเมล, ยืนยันอีเมล, เข้าสู่ระบบ, รีเซ็ตรหัสผ่าน (รหัสผ่านถูกแฮชด้วย bcrypt ฝั่งเซิร์ฟเวอร์) |
| **PostgreSQL** | เก็บบันทึกการนอนและโปรไฟล์ผู้ใช้ |
| **Row Level Security** | ผู้ใช้อ่าน/เขียนได้เฉพาะข้อมูลของตัวเอง |
| **REST (PostgREST)** | Front End เรียกตรงผ่าน `/rest/v1/...` |

**ตาราง**

| ตาราง | คอลัมน์หลัก |
|---|---|
| `entries` | `user_id`, `date` (วันที่ตื่น, unique ต่อผู้ใช้), `bed`, `wake`, `lat`, `awk`, `in_bed`, `asleep`, `eff`, `rating`, `factors`, `note`, `mood`, `bed_at`, `wake_at`, `tz`, `bed_tz` |
| `profiles` | `user_id`, `name`, `goal_min`, `onboarded`, `prefs` (jsonb: ชื่อที่แสดง, รูปโปรไฟล์, เป้าเวลาเข้านอน, session ที่กำลังจับเวลา, ความยินยอม ฯลฯ) |

ฟังก์ชัน RPC `delete_my_account` ใช้ลบบัญชีและข้อมูลทั้งหมดของผู้ใช้

**การซิงก์ข้อมูล** — ทุกการแก้ไขเข้าคิวในเครื่องก่อน แล้วส่งขึ้นเซิร์ฟเวอร์เมื่อออนไลน์ จึงใช้งานออฟไลน์ได้ และข้อมูลตามผู้ใช้ไปทุกอุปกรณ์

### Stats service
บริการ Python สำหรับงานสถิติ แพ็กเป็น Docker image และรันที่พอร์ต `8000` (ดูวิธีรันใน [Getting Started](#-getting-started))

## 🚀 Getting Started

feature/good-night-webapp
### Good Night web app

The supplied sleep tracker is available as a static app in [`web/`](web/index.html). Run it locally in local-only mode with `python -m http.server 4173 --directory web`, then open `http://localhost:4173`. For Supabase cloud mode, schema/RLS, Auth redirect, and account-deletion setup, follow [`docs/good-night-setup.md`](docs/good-night-setup.md). The original Docker instructions below still apply to the separate Python stats service.

This section explains how to get a local copy of the project up and running for development and testing purposes.
=======

### Prerequisites

- Git
- Node.js 18+ (สำหรับรัน tests)
- Python 3.10+
- Docker & Docker Compose
- บัญชี [Supabase](https://supabase.com/) (ฟรี) — ถ้าต้องการบัญชีที่ใช้ข้ามอุปกรณ์ได้

### 1. Clone the repository
```bash
git clone [your-repository-url]
cd [your-project-folder]
```

### 2. รัน Front End
เป็น static site จึงเปิดผ่าน local server ตัวไหนก็ได้
```bash
npx serve .
# หรือ
python -m http.server 5173
```
แล้วเปิด `http://localhost:5173` (หรือพอร์ตที่ server แจ้ง)

### 3. เชื่อมต่อ Supabase
1. สร้างโปรเจกต์ใน Supabase
2. เปิด **SQL Editor** แล้วรัน `supabase.sql` ตามด้วย `supabase-migration.sql`
3. ไปที่ **Authentication › Providers › Email** ตั้ง *Minimum password length* = `8`
4. ใส่ค่าใน `GN_CONFIG` ภายในไฟล์ HTML

```js
window.GN_CONFIG = {
  supabaseUrl: 'https://<project-id>.supabase.co',
  supabaseAnonKey: '<anon public key>',   // ใส่ในเบราว์เซอร์ได้ ข้อมูลถูกป้องกันด้วย RLS
  schemaV2: true,                         // หลังรัน supabase-migration.sql แล้ว
  privacyContact: 'contact@example.com'   // แสดงในนโยบายความเป็นส่วนตัว
};
```

> ถ้าเว้น `supabaseUrl` / `supabaseAnonKey` ว่างไว้ แอปยังใช้งานได้ โดยเก็บบัญชีและข้อมูลไว้ในเบราว์เซอร์ของเครื่องนั้น (เหมาะกับการพัฒนาและทดสอบ)

### 4. รัน Stats service (Docker)
*(ส่วนนี้จะอัปเดตเมื่อย้ายไปใช้ Docker Compose)*
```bash
# Build from the repository root using the Lab 6 Dockerfile
docker build -t adisakx2548/stats-service:v0.1.0 .
docker run --rm -p 8000:8000 adisakx2548/stats-service:v0.1.0
```

## 🧪 การทดสอบ

Tests อ่านโค้ดจากไฟล์ HTML ตัวจริงที่ deploy มาทดสอบ จึงมั่นใจได้ว่าสิ่งที่ผ่านการทดสอบคือสิ่งที่ผู้ใช้ใช้งานจริง

```bash
npm test          # = node --test
```

ครอบคลุม: การคำนวณการนอน, Sleep Score, ช่วงวันที่ 7 วัน/รายเดือน, session จับเวลา (ข้ามเที่ยงคืน, เปลี่ยนเขตเวลา, กดซ้ำ), เป้าหมายและคำแนะนำเวลาเข้านอน, วิเคราะห์ปัจจัย, การส่งออก CSV, bcrypt (เทียบกับ test vectors และ PHP `password_hash`) และการตรวจกฎสำคัญในตัวแอป (รหัสผ่าน ≥ 8 ตัว, ต้องยินยอมก่อนบันทึก ฯลฯ)

**CI** — GitHub Actions (`.github/workflows/test.yml`) รัน tests อัตโนมัติทุก push และ pull request

## 🔐 ความปลอดภัยและความเป็นส่วนตัว

- รหัสผ่านอย่างน้อย **8 ตัวอักษร** และไม่เก็บรหัสผ่านแบบอ่านออกได้ — แฮชด้วย **bcrypt**
- ผู้ใช้เข้าถึงได้เฉพาะข้อมูลของตัวเอง (Supabase Row Level Security)
- **ขอความยินยอมก่อนเก็บข้อมูล** และบันทึกเวอร์ชัน/เวลาที่ยินยอม
- ผู้ใช้ **ดู ส่งออก แก้ไข ลบ** ข้อมูลของตัวเองได้ และ **ถอนความยินยอม** ได้ทุกเมื่อ (ลบบัญชีและข้อมูลทั้งหมด)
- อายุที่กรอกเพื่อดูช่วงชั่วโมงนอนที่แนะนำ **ไม่ถูกเก็บ**
- ไม่มีโฆษณา ไม่ขายหรือเปิดเผยข้อมูลให้บุคคลอื่น

## 🤝 Ways of Working

เอกสารนี้กำหนดวิธีการทำงานร่วมกันของทีม เป็นข้อตกลงที่ปรับเปลี่ยนได้เสมอ — ถ้ามีจุดไหนไม่เวิร์ค ให้ยกขึ้นมาคุยใน Retrospective แล้วปรับปรุงร่วมกัน

### 1. ความถี่ของการประชุม (Meeting Cadence)

| การประชุม | ความถี่ | ระยะเวลา | จุดประสงค์ |
|---|---|---|---|
| **Sprint Planning** | 1 ครั้ง/สปรินต์ (ต้น sprint) | 45–60 นาที | กำหนดเป้าหมายของ sprint, แบ่งและมอบหมายงานจาก backlog |
| **Daily Stand-up** | สัปดาห์ละ 3 วัน (เช่น จ./พ./ศ.) | 10–15 นาที | อัปเดตสั้นๆ: ทำอะไรไปแล้ว, กำลังทำอะไร, มีอะไรติดขัด |
| **Mid-Sprint Check-in** | 1 ครั้ง/สปรินต์ (กลาง sprint) | 15–20 นาที | ดักจับปัญหา scope ที่บวมเกินหรือ blocker ตั้งแต่เนิ่นๆ |
| **Sprint Review/Demo** | 1 ครั้ง/สปรินต์ (ปลาย sprint) | 20–30 นาที | สาธิตฟีเจอร์ที่ทำเสร็จให้ทีม (และอาจารย์/ผู้ดูแลโปรเจกต์) ดู |
| **Retrospective** | 1 ครั้ง/สปรินต์ (หลัง Review) | 20–30 นาที | คุยว่าอะไรไปดี/ไม่ดี และหา action item 1 ข้อไปลองทำใน sprint ถัดไป |

**หมายเหตุ:**
- Daily Stand-up ในทางปฏิบัติคือ 3 วัน/สัปดาห์ เพราะทีมนักศึกษามีตารางเรียนชนกัน ไม่จำเป็นต้องทุกวัน วันที่ไม่มีประชุมให้อัปเดตผ่านข้อความ (เช่น thread ใน Discord/Slack) แทนได้
- แนะนำให้ใช้ **sprint ละ 1 สัปดาห์** เพื่อให้ feedback loop สั้นและไม่หลุดทิศทางนาน
- ทุกการประชุมต้อง timebox เสมอ — ถ้าประชุมมีแนวโน้มจะยาวเกินกำหนด แสดงว่าเรื่องนั้นควรย้ายไปคุยแบบ async แทน


### 2. กฎการสื่อสาร (Communication Rules)

**ช่องทางหลัก:** Instagram Group Chat, Discord

- **เวลาตอบกลับที่คาดหวัง:** ตอบรับข้อความภายใน **24 ชั่วโมง** ในวันธรรมดา "ตอบรับ" ไม่ได้แปลว่าต้องตอบครบทุกอย่าง แค่กด 👍 หรือพิมพ์ "เดี๋ยวเช็คให้ จะตอบคืนนี้" ก็ถือว่าผ่าน
- **ใช้ Thread ไม่ใช่สแปมในช่องหลัก:** การสนทนาที่ยาวเกิน 2–3 ข้อความในประเด็นเดียวกัน ให้ย้ายไปคุยใน **thread** เพื่อให้ช่องหลักอ่านง่าย ไม่รก
- **DM กับการพูดในที่สาธารณะ:** ให้คุยเรื่องที่เกี่ยวกับโปรเจกต์ในช่องทางสาธารณะเป็นหลัก — ทั้งการตัดสินใจ, blocker, คำถามต่างๆ แม้จะรู้สึกว่าเป็นแค่ "คำถามเล็กๆ" ก็ตาม เพื่อให้ทุกคนรับรู้ข้อมูลเท่ากันและไม่เกิดความรู้ที่กระจุกอยู่กับคนใดคนหนึ่ง ส่วน DM ใช้เฉพาะเรื่องส่วนตัวหรือเรื่องที่ละเอียดอ่อนจริงๆ
- **แจ้ง Blocker ทันที** ไม่ต้องรอถึงวันประชุมครั้งต่อไป เพราะ blocker ที่ถูกเก็บไว้เงียบๆ 2 วัน คือความเสี่ยงของทั้งทีม
- **ห้าม "หายเงียบ"** ถ้าทำงานไม่ทันตามกำหนด หรือเข้าประชุมไม่ได้ ให้บอกล่วงหน้า อย่าเงียบไปเฉยๆ — เข้าใจว่าทุกคนมีชีวิตส่วนตัว แค่ขอให้แจ้งทีมก่อน
- **แท็กให้ตรงจุด** ใช้ @mention เฉพาะเมื่อต้องการให้คนนั้นลงมือทำอะไรจริงๆ ไม่ใช่แท็กพร่ำเพรื่อสำหรับอัปเดตทั่วไป


### 3. Git Workflow

**โมเดล Branching:** Simplified Git Flow

```
main          → โค้ดที่เสถียรและพร้อม deploy เสมอ
develop       → branch รวมงาน, โค้ดเวอร์ชันล่าสุดที่ใช้งานได้
feature/*     → feature/sleep-quality-chart
fix/*         → fix/timezone-bug
```

- งานทุกอย่างทำบน branch `feature/*` หรือ `fix/*` ที่แตกออกมาจาก `develop`
- **ห้าม commit ตรงเข้า `main` หรือ `develop` เด็ดขาด**
- การตั้งชื่อ branch: `feature/short-description` หรือ `fix/short-description` (ตัวพิมพ์เล็ก, ใช้ขีดกลาง)

**Commit Message:**
- ใช้รูปแบบ: `type: คำอธิบายสั้นๆ` (เช่น `feat: add sleep duration chart`, `fix: correct timezone bug in sleep log`)
- ประเภทที่ใช้บ่อย: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`
- บรรทัดแรกไม่ควรเกิน ~50 ตัวอักษร ถ้าต้องการรายละเอียดเพิ่ม ให้เขียนต่อในบรรทัดถัดไป

**Pull Request:**
- เปิด PR จาก branch `feature/*` ของคุณ เข้าไปที่ `develop`
- รายละเอียดใน PR ต้องระบุ: เปลี่ยนแปลงอะไร, ทำไม, และทดสอบยังไง (แค่ 2–3 bullet point ก็พอ)
- **ต้องมีสมาชิกอีกคนอย่างน้อย 1 คน รีวิวและอนุมัติก่อนจึง merge ได้** ห้าม merge งานของตัวเอง
- สิ่งที่ผู้รีวิวต้องเช็ค: โค้ดทำงานได้จริงไหม, อ่านเข้าใจไหม, ตรงตาม pattern ที่ใช้อยู่ในโปรเจกต์ไหม — ไม่ใช่การจับผิดเรื่องเล็กๆ
- ต้องแก้ไข comment ที่รีวิวให้ครบก่อน merge (หรือถ้าไม่เห็นด้วยก็ต้องคุยกันให้ชัดเจนก่อน)
- ใช้ **"Squash and merge"** เพื่อให้ history ของ `develop` สะอาด
- ลบ branch ทิ้งหลัง merge เสร็จ
- merge จาก `develop` เข้า `main` เฉพาะตอนปลาย sprint เมื่อ build มั่นใจว่าเสถียรแล้ว (เช่น หลังจาก demo)


### 4. การตัดสินใจ (Decision Making)

ใช้แนวทางแบบลำดับขั้น — ส่วนใหญ่ไม่ต้องประชุมก็ตัดสินใจได้ แต่บางเรื่องต้องคุยกัน:

1. **เรื่องเล็กที่ปรับเปลี่ยนได้ง่าย** (ชื่อตัวแปร, UI ปรับเล็กน้อย, เลือก library สำหรับฟีเจอร์ที่ไม่สำคัญมาก): **ให้คนที่ลงมือทำงานนั้นตัดสินใจเอง** ไม่ต้องรอ consensus สำหรับเรื่องที่แก้ไขทีหลังได้ง่าย
2. **เรื่องที่กระทบทั้งทีม** (architecture โดยรวม, เทคโนโลยีหลักที่ใช้, data model, API contract): คุยกันในที่ประชุมหรือ thread โดย **มุ่งหา consensus** ให้ทุกคนมีโอกาสแสดงความเห็นก่อนตัดสินใจ
3. **ถ้าหา consensus ไม่ได้หลังจากคุยกันพอสมควรแล้ว** (timebox ไว้ — แค่ 15 นาทีก็พอที่จะเห็น trade-off ที่แท้จริง): ให้ใช้วิธี **โหวต** เสียงข้างมากชนะ
4. **ถ้าโหวตเสมอกัน หรือทีมตกลงกันไม่ได้จริงๆ** ให้ **Tech Lead ที่กำหนดไว้** เป็นผู้ชี้ขาด (จะหมุนเวียนตำแหน่งนี้ทุก sprint หรือกำหนดตายตัวทั้งโปรเจกต์ก็ได้ ตามที่ทีมตกลงกัน)
5. **บันทึกการตัดสินใจไว้เสมอ** — แค่โน้ตสั้นๆในช่องแชทหรือ README ("ตัดสินใจ: ใช้ SQLite สำหรับ MVP ค่อยพิจารณาเปลี่ยนทีหลังถ้าต้อง scale") เพื่อไม่ต้องเถียงเรื่องเดิมซ้ำอีกใน 2 สัปดาห์ข้างหน้าโดยไม่มีข้อมูลใหม่

**หลักการ:** Disagree and commit — ไม่เห็นด้วยก็ทำตาม เมื่อตัดสินใจแล้ว ทีมต้องเดินหน้าไปด้วยกัน แม้บางคนจะยังไม่เห็นด้วย 100% ก็ตาม ความกังวลสามารถนำมาคุยใหม่ได้ถ้ามีข้อมูลใหม่เข้ามา แต่ไม่ใช่การรื้อประเด็นเดิมขึ้นมาเถียงซ้ำทุก sprint
