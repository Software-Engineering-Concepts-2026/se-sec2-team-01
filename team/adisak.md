## 4. Broken Window ที่เคยเจอ พร้อมผลกระทบและสิ่งที่จะป้องกัน
* **Broken Window ที่เคยเจอ:** การปล่อยให้มีโค้ดที่ไม่ได้ใช้ (Dead Code), การตั้งชื่อตัวแปรแบบย่อที่เข้าใจยาก (เช่น `a`, `temp2`), และการข้ามการจัดการ Error Handling ("เดี๋ยวค่อยกลับมาแก้")
* **ผลกระทบ:** เมื่อคนในทีมเห็นว่ามีจุดที่เขียนโค้ดลวกๆ ได้ คนต่อๆ ไปก็จะเริ่มหย่อนมาตรฐานตาม ทำให้หนี้ทางเทคนิค (Technical Debt) พอกพูนอย่างรวดเร็ว โค้ดอ่านยากขึ้น และเกิด Bug ที่หาสาเหตุได้ยากเวลา Production
* **แนวทางป้องกัน:**
  1. ยึดหลัก **Boy Scout Rule** คือ "ทิ้งโค้ดไว้ให้สะอาดกว่าตอนที่เราเปิดดูเสมอ"
  2. ตั้งค่า **Linter & Formatter** อัตโนมัติในโปรเจกต์เพื่อบังคับใช้มาตรฐานเดียวกัน
  3. ปฏิเสธการ Approve PR ที่มี Broken Windows โดยให้แก้จุดเล็กๆ เหล่านั้นทันทีก่อน Merge
