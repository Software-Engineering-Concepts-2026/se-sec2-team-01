## Pragmatic Promise

ผมจะทำงานบน branch ของตนเอง แบ่งงานเป็น commit ขนาดเล็กที่อธิบายได้ และใช้ Conventional Commit ให้สื่อว่าการเปลี่ยนแปลงนั้นทำอะไร ก่อนส่ง Pull Request ผมจะตรวจ diff และทดสอบงานตามวิธีที่เหมาะสมกับไฟล์หรือฟีเจอร์นั้นทุกครั้ง

เมื่อพบปัญหาหรือทำงานไม่ทัน ผมจะรีบแจ้งทีมพร้อมเสนอทางเลือกอย่างน้อยสองทาง เช่น ลด scope ชั่วคราว แบ่งงานให้สมาชิกช่วย หรือขอปรับลำดับความสำคัญ แทนการปล่อย blocker ไว้เงียบ ๆ และเมื่อพบ Broken Window ในโค้ดหรือเอกสาร ผมจะบันทึกและแก้ไขจุดที่มีผลกระทบก่อนงานจะขยายตัว

ผมจะอ่าน feedback จาก reviewer อย่างตั้งใจและตอบให้ครบว่าปรับแก้หรือมีเหตุผลอะไรที่ยังไม่ปรับ เพราะการ review ไม่ใช่ขั้นตอนเพื่อหาคนผิด แต่เป็นวิธีช่วยให้ทีมค้นหาความเสี่ยงก่อนส่งมอบ ผู้ใช้และสมาชิกคนอื่นควรสามารถเข้าใจเหตุผลของการเปลี่ยนแปลงได้จาก commit, Pull Request และเอกสารที่เกี่ยวข้อง

ผมจะเก็บหลักฐานการทำงานไว้ใน issue, branch, commit, review, test และ README ให้ตรวจสอบย้อนหลังได้

## ทำไมอยากเรียน Software Engineering

ผมอยากเข้าใจการพัฒนาซอฟต์แวร์ให้เป็นระบบมากกว่าการเขียนโค้ดให้รันผ่านเพียงอย่างเดียว โดยเฉพาะการวิเคราะห์ requirements การออกแบบ architecture การทดสอบ และการทำงานร่วมกันผ่าน Git และ code review ความรู้เหล่านี้จะช่วยให้ผมสร้างซอฟต์แวร์ที่ดูแลต่อได้ ไม่ผูกติดกับคนเขียนเพียงคนเดียว และปรับเปลี่ยนได้เมื่อความต้องการของผู้ใช้เปลี่ยนไป

ผมยังต้องการฝึกสื่อสารการตัดสินใจทางเทคนิคกับทีมให้ชัดเจน เพราะซอฟต์แวร์ที่ดีไม่ได้วัดจากโค้ดอย่างเดียว แต่รวมถึงการส่งมอบที่ตรวจสอบได้ การรับผิดชอบต่อผลลัพธ์ และการปรับปรุงกระบวนการจาก feedback จริง

ผมอยากนำแนวคิดเหล่านี้ไปใช้ตั้งแต่ต้นโครงการ เช่น ถามให้ชัดว่าผู้ใช้ต้องการอะไร กำหนดขอบเขตที่ทีมทำได้จริง และเลือกวิธีแก้ที่เหมาะกับบริบทแทนการทำตามเครื่องมือหรือรูปแบบที่กำลังเป็นที่นิยมโดยไม่เข้าใจเหตุผล การเรียน SE จะช่วยให้ผมมองเห็น trade-off และอธิบายการตัดสินใจได้ดีขึ้น

สิ่งที่ผมคาดหวังคือสามารถทำงานกับเพื่อนในทีมได้อย่างมีความรับผิดชอบมากขึ้น รู้จักขอความช่วยเหลือเมื่อจำเป็น และเปลี่ยน feedback ให้เป็นการปรับปรุงที่เห็นผลจริง ไม่ใช่เพียงทำงานให้เสร็จตามกำหนดแล้วปล่อยให้ปัญหาถูกส่งต่อไปยังคนอื่น

## Broken Window ที่เคยเจอ

### 1. Window คืออะไร?

ในโปรเจกต์ที่ผ่านมา ผมเคยเจอการปล่อยให้โครงสร้างโฟลเดอร์และการตั้งชื่อไฟล์ไม่เป็นระเบียบ เพราะทีมคิดว่าจะกลับมาแก้ภายหลัง ปัญหาเล็ก ๆ นี้เป็น Broken Window เพราะทุกคนเห็นว่ามาตรฐานยังไม่ชัดเจนและเริ่มเพิ่มโค้ดตามทางลัดของตนเอง

### 2. ผลกระทบที่เกิดขึ้น

เมื่อโค้ดและชื่อไฟล์ไม่สม่ำเสมอ สมาชิกใหม่ค้นหาส่วนที่ต้องแก้ได้ยาก เกิดความเข้าใจผิดเกี่ยวกับตำแหน่งและหน้าที่ของไฟล์ และใช้เวลา debug มากขึ้น การแก้ฟีเจอร์หนึ่งจึงกระทบส่วนอื่นได้ง่ายกว่าที่ควรจะเป็น

### 3. ถ้าแก้ทันทีจะป้องกันอะไร?

ถ้าทีมกำหนด naming และ folder convention ตั้งแต่แรก พร้อมแก้จุดผิดทันทีในการ review จะป้องกันการสะสมของ technical debt ลดการเขียน workaround และทำให้เพื่อนร่วมทีมอ่าน ตรวจสอบ และต่อยอดงานได้ง่ายขึ้น

นอกจากการจัดชื่อไฟล์แล้ว ทีมควรลบโค้ดที่ไม่ใช้ อัปเดต README เมื่อโครงสร้างเปลี่ยน และทิ้งโน้ตสั้น ๆ ไว้เมื่อมีการตัดสินใจสำคัญ วิธีนี้ช่วยให้หน้าต่างที่เริ่มแตกถูกซ่อมตั้งแต่ขนาดเล็ก ไม่กลายเป็นปัญหาใหญ่ที่ต้องเสียเวลารื้อระบบก่อนส่งงานหรือก่อนเริ่มฟีเจอร์ถัดไป
