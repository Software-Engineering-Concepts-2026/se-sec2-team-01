"จากแนวคิด 'Software Entropy' และ 'Broken Window Theory' ลองมองย้อนกลับไปในโปรเจกต์ที่คุณเคยทำ มี 'หน้าต่างที่แตก' บานไหนที่คุณเคยปล่อยปละละเลย และมันส่งผลกระทบอย่างไรในระยะยาว?"
Answer: มีเรื่องการใช้ api ที่ตอนแรกวางไว้เป็นอีกตัว แต่พอ dev จริงแล้วเกิดปัญหาด้านการสื่อสารแล้วกลายเป็นใช้อีกตัวแทน แล้วสมาชิกในทีมก็ปล่อยปละละเลย ทำให้เวลา push เว็บขึ้น server จริง ๆ แล้ว กลายเป็นว่า เว็บมันไม่มีประสิทธิภาพเท่าที่ควร เพราะ api ที่ใช้มันมีประสิธิภาพน้อยกว่าตัวที่วางแผนไว้ จนสุดท้าย ต้องเปลี่ยนกลับไปใช้ตามที่วางแผน

"อธิบายหลักการ 'Take Responsibility' ในความเข้าใจของคุณ และยกตัวอย่างสถานการณ์ที่คุณจะนำหลักการ 'Provide Options, Don't Make Lame Excuses' ไปใช้ในการสื่อสารกับเพื่อนร่วมทีมในโปรเจกต์นี้"
Answer: คือการกล้าหรือพร้อมที่จะรับผิดชอบต่อหน้าที่หรืองานที่ตัวเองได้รับมอบหมาย นั่นคือ เมื่อได้รับมอบหมายให้ทำงานนั้น ๆ มาแล้ว ก็ควรจะต้องรับผิดชอบหากเกิดปัญหาหรือข้อผิดพลาดขึ้นกับงาน และไม่ใช่การรับผิดชอบแบบปากเปล่าหรือกล่าวโทษไปเรื่อย แต่เป็นการรับผิดชอบโดยการยอมรับความผิดในส่วนของตัวเอง และหาหนทางเพื่อแก้ปัญหาหรือความผิดพลาดนั้น ๆ ยกตัวอย่างเช่น เมื่อเราทำงานผิดพลาด ทำให้ระบบเกิดข้อบกพร่อง ก็ควรจะยอมรับและหาหนทางแก้ไขว่าจะทำยังไงต่อ แก้ไขยังไงได้บ้าง ลิสต์ออกมาและหาหนทางที่ดีที่สุด เป็นต้น
