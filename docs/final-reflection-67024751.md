## 1. What did you build?

ผมร่วมพัฒนา Good Night เว็บแอปที่ช่วยบันทึกเวลานอนและพฤติกรรมที่เกี่ยวข้อง แล้วนำข้อมูลมาแสดงเป็นภาพรวม ประวัติ สถิติ และคำแนะนำ ตัวแอปมีทั้งการเริ่มจับเวลานอน–ตื่น การบันทึกรายคืน และ Sleep Score ที่อธิบายองค์ประกอบให้ผู้ใช้เข้าใจได้

ในงานที่ส่งผ่าน PR #60 ทีมเพิ่มตัวแอปไว้ใน `web/` พร้อมแนวทางเชื่อม Supabase, schema และ RLS, เอกสารตั้งค่า, การทดสอบ และ workflow สำหรับเผยแพร่เว็บ ส่วนการตัดสินใจให้หน้าเว็บเป็น static app และแยกขอบเขต cloud/local บันทึกไว้ใน ADR 0002 งานนี้ทำให้เห็นภาพตั้งแต่หน้าจอที่ผู้ใช้กด ไปจนถึงข้อมูลและขั้นตอนส่งมอบ ไม่ใช่แค่ทำหน้า prototype ให้ดูได้

## 2. What problem did you solve?

ปัญหาหลักคือผู้ใช้มักรู้เพียงว่าเมื่อคืนรู้สึกนอนดีหรือไม่ แต่ไม่เห็นภาพรวมว่าระยะเวลาหลับ ประสิทธิภาพ ความสดชื่น และพฤติกรรมอย่างคาเฟอีนหรือการออกกำลังกายสัมพันธ์กันอย่างไร Good Night จึงรวบรวมข้อมูลเหล่านี้ไว้ในบันทึกเดียวและแสดงแนวโน้ม เพื่อให้ผู้ใช้สังเกตแบบแผนของตนเองได้ง่ายขึ้น

ระบบนี้เป็นเครื่องมือช่วยติดตาม ไม่ใช่เครื่องมือวินิจฉัยโรค จุดสำคัญคือช่วยให้ข้อมูลอ่านและนำไปทดลองปรับพฤติกรรมได้ โดยไม่สรุปเกินกว่าข้อมูลที่ผู้ใช้บันทึกไว้

## 3. What technical decision are you proudest of?

ผมภูมิใจที่ทีมกำหนดขอบเขตของ Good Night ให้เหมาะกับสิ่งที่มีอยู่: คงหน้าเว็บแบบ static ที่ทดสอบการคำนวณได้ไว้ แทนการย้ายไป framework ใหม่ทั้งชุด และใช้ Supabase เป็นทางเลือกสำหรับบัญชีและการซิงก์ข้อมูล โดยยังมี local mode สำหรับพัฒนาและทดลอง แนวทางนี้บันทึกไว้ใน [ADR 0002](architecture/adr/0002-good-night-frontend-and-supabase.md) และระบุชัดว่าไม่ไปเปลี่ยน Stats Service ของงานส่วนอื่น

การแบ่ง local/cloud ช่วยให้ทีมพัฒนาหน้าจอและทดสอบ flow ได้โดยไม่ต้องทำให้ทุกคนเริ่มจากการตั้งค่าบัญชี cloud ก่อน ขณะเดียวกันข้อมูลที่จะใช้จริงต้องผ่าน Auth และ RLS ไม่ควรฝังคีย์ลับไว้ใน browser การตัดสินใจนี้ทำให้เห็น trade-off ระหว่างความเร็วในการทำงานกับความปลอดภัยและการดูแลระบบ

## 4. What failure taught you the most?

ตอนทดสอบสมัครบัญชี เคยเจอข้อความ `Email signups are disabled` ทั้งที่หน้าตั้งค่าที่ตรวจดูแสดงว่าเปิดการสมัครไว้ เหตุการณ์นี้ทำให้เห็นว่าการเช็ก toggle เพียงจุดเดียวไม่ได้พิสูจน์ว่า flow สมัครพร้อมใช้งาน และจากภาพหน้าจออย่างเดียวก็ยังสรุปสาเหตุไม่ได้

บทเรียนที่ได้คือทดสอบจากมุมผู้ใช้จริงให้ครบตั้งแต่หน้าสมัคร การตั้งค่า Auth และ redirect ของ environment นั้น ไปจนถึงการเข้าสู่ระบบและบันทึกข้อมูล หากติดขัดควรตรวจ response/error ที่ระบบส่งกลับก่อนแก้แบบเดาสุ่ม และไม่ควรประกาศว่าฟีเจอร์พร้อมเพียงเพราะหน้า UI แสดงผลถูกต้อง

## 5. What would you do differently?

ถ้าเริ่มใหม่ ผมจะทำสามอย่างตั้งแต่ต้น:

1. **กำหนด test path สำหรับบัญชีและข้อมูลให้ชัด:** ใช้บัญชีทดสอบที่ไม่มีข้อมูลจริง แล้วทดลองสมัคร เข้าสู่ระบบ บันทึกหนึ่งคืน รีเฟรชหน้า และตรวจว่าข้อมูลยังอยู่ครบทั้ง local mode และ cloud mode
2. **ทำรายการตั้งค่าแต่ละ environment:** แยกค่าที่เปิดเผยได้กับ secret ให้ชัด ใช้ไฟล์ตัวอย่างสำหรับชื่อตัวแปร และเขียนขั้นตอนตั้งค่า Auth/redirect โดยไม่ใส่ค่าลับลง repository
3. **ทดสอบ integration ก่อนทำ polish รอบสุดท้าย:** เริ่มจาก flow หลักและกรณีผิดพลาด เช่น ไม่มีข้อมูล ยังไม่ได้เข้าสู่ระบบ หรือ API ใช้งานไม่ได้ แล้วค่อยปรับรายละเอียดหน้าตา เพื่อไม่ให้ปัญหาการเชื่อมระบบไปโผล่ตอนเตรียม demo

## 6. How did you embody Tip 52 (Delight Users)?

- **ลดขั้นตอนของการบันทึก:** ผู้ใช้เริ่มนอนและกดตื่นเพื่อสร้างบันทึกได้ ไม่ต้องคำนวณเวลาทุกช่องด้วยตนเอง
- **ทำคะแนนให้อธิบายได้:** หน้าแอปแสดงส่วนประกอบของ Sleep Score ได้แก่ ระยะเวลาหลับจริงเทียบเป้าหมาย 50%, ประสิทธิภาพ 30% และความสดชื่น 20%; ถ้าไม่ให้คะแนนความสดชื่น ระบบปรับน้ำหนักของส่วนที่เหลือ ไม่แสดงคะแนนเหมือนเป็นข้อสรุปทางการแพทย์
- **ให้ผู้ใช้เข้าใจข้อมูลก่อนเรียก AI:** ส่วนคำแนะนำอธิบายชนิดข้อมูลย้อนหลังที่ส่งไปประมวลผล และแจ้งว่าไม่ใช่คำแนะนำทางการแพทย์ พร้อมมีข้อความ fallback เมื่อบริการ AI ใช้ไม่ได้ เพื่อให้ผู้ใช้ยังเข้าถึงคำแนะนำระบบเดิมได้

สำหรับผม Delight ไม่ได้แปลว่าต้องเพิ่มลูกเล่นมากที่สุด แต่คือทำให้ผู้ใช้เข้าใจว่าต้องทำอะไร ข้อมูลของตนถูกใช้อย่างไร และระบบมีข้อจำกัดตรงไหน
