# Scenarios — Good Night

Scenarios เหล่านี้ต่อยอดจาก persona 2 คนเดิมและใช้เป็น traceability source ให้กับ user stories ใน `user-stories.md`

## SC-T01 — ต้นตั้งเป้าหมายและเริ่มใช้งานครั้งแรก

**Persona:** ต้น — Health-Optimizing User<br>
**Objective:** ตั้ง baseline สำหรับการติดตามการนอนโดยไม่ต้องกรอกข้อมูลจำนวนมาก

ต้นเปิด Good Night หลังจากเห็นรีวิวจากเพื่อนร่วมงาน เขาเลือกเป้าหมายเวลานอน 7–9 ชั่วโมง ระบุเวลาเข้านอนที่ต้องการ และอ่านคำอธิบายว่าระบบจะใช้ข้อมูลสุขภาพอย่างไร จากนั้นเขาเลือกปัจจัยที่ต้องการติดตาม เช่น คาเฟอีน การออกกำลังกาย และ screen time ระบบแสดงสรุปการตั้งค่าให้ตรวจสอบก่อนบันทึก

**Action sequence:**

1. เปิดหน้า onboarding และเลือกเป้าหมายการนอน
2. ระบุเวลาเข้านอนและเวลาตื่นที่ต้องการ
3. เลือก activity tags ที่สนใจ
4. อ่าน privacy notice และยืนยันการตั้งค่า
5. ระบบสร้าง baseline profile และพาไปหน้า dashboard

**ปัญหา/edge case:** ต้นไม่ต้องการเชื่อมต่อ smartwatch ในช่วงแรก หรือข้าม activity tag บางรายการ ระบบต้องให้เริ่มใช้งานได้โดยไม่บังคับข้อมูลที่ยังไม่จำเป็น

**ผลลัพธ์ที่คาดหวัง:** ต้นเริ่มบันทึกข้อมูลได้ภายในไม่กี่นาที และรู้ว่าระบบจะแสดง insight จากข้อมูลใด

## SC-T02 — ต้นตรวจ dashboard ตอนเช้าแบบรวดเร็ว

**Persona:** ต้น<br>
**Objective:** เข้าใจสถานะการนอนเมื่อคืนและแนวโน้มโดยใช้เวลาไม่เกิน 5–10 นาที

ตอนเช้าขณะดื่มกาแฟ ต้นเปิด dashboard ระบบแสดง sleep score, ชั่วโมงการนอน, เวลาเข้านอน และ trend 7 วันในหน้าจอเดียว เขากดวันที่มีคะแนนต่ำเพื่อดูรายละเอียดและเห็นว่าคืนดังกล่าวมีการดื่มกาแฟช่วงบ่าย ต้นจึงตัดสินใจปรับพฤติกรรมในวันถัดไป

**Action sequence:**

1. เปิด dashboard หลังตื่นนอน
2. ดูสรุปเมื่อคืนและค่าเฉลี่ย 7 วัน
3. เลือกวันที่ต้องการดูรายละเอียด
4. ตรวจ activity tags และเหตุผลของ insight
5. บันทึกสิ่งที่ต้องลองปรับในวันถัดไป

**ปัญหา/edge case:** หากมีข้อมูลน้อยกว่า 3 คืน ระบบต้องแสดง empty state หรือคำเตือนว่า trend ยังไม่น่าเชื่อถือ แทนการคำนวณสรุปที่ชวนเข้าใจผิด

**ผลลัพธ์ที่คาดหวัง:** ต้นเข้าใจข้อมูลสำคัญได้เร็วและแยกข้อมูลจริงออกจากคำแนะนำที่ยังเป็นเพียงสมมติฐาน

## SC-T03 — ต้นเปรียบเทียบพฤติกรรมกับ trend รายสัปดาห์

**Persona:** ต้น<br>
**Objective:** ตรวจว่าการออกกำลังกายและคาเฟอีนสัมพันธ์กับ sleep quality ของตนเองหรือไม่

หลังใช้งานต่อเนื่องหนึ่งสัปดาห์ ต้นเปิด weekly report และเลือก filter “ออกกำลังกาย” ระบบเปรียบเทียบคืนที่มีและไม่มี tag พร้อมแสดงจำนวนคืนที่ใช้คำนวณ เขาตรวจ raw records ก่อนสรุปว่า pattern เป็นเพียง correlation ไม่ใช่ข้อพิสูจน์เชิงสาเหตุ

**Action sequence:**

1. เปิด weekly trend
2. เลือก activity tag ที่ต้องการวิเคราะห์
3. ดูค่าเฉลี่ยและจำนวน records ของแต่ละกลุ่ม
4. เปิดรายละเอียดคืนที่นำมาคำนวณ
5. บันทึกสมมติฐานเพื่อทดลองในสัปดาห์ถัดไป

**ปัญหา/edge case:** ถ้าจำนวน records ของกลุ่มใดน้อยเกินไป ระบบต้องระบุว่า “ข้อมูลยังไม่พอ” และไม่แสดงข้อความสรุปที่ฟันธง

**ผลลัพธ์ที่คาดหวัง:** ต้นเห็นหลักฐานที่ตรวจสอบย้อนกลับได้และเลือกพฤติกรรมที่จะทดลองต่อได้อย่างมีเหตุผล

## SC-T04 — ต้นตรวจเหตุผลของคำแนะนำและ privacy

**Persona:** ต้น<br>
**Objective:** เข้าใจว่าคำแนะนำเกิดจากข้อมูลใดและควบคุมการใช้ข้อมูลของตนเองได้

ต้นได้รับคำแนะนำให้ลด screen time ก่อนนอน เขากด “ทำไมจึงแนะนำ” ระบบแสดง records และ rule ที่ใช้ประกอบคำแนะนำ พร้อมแสดงวันที่ข้อมูลถูกเก็บ ต้นเข้า privacy settings เพื่อตรวจสิทธิ์การใช้งานและเลือกว่าจะเปิดหรือปิด notification

**Action sequence:**

1. เปิดคำแนะนำจาก dashboard
2. กดดูเหตุผลและ records ที่เกี่ยวข้อง
3. ตรวจวันที่และจำนวนข้อมูลที่ใช้คำนวณ
4. เปิด privacy settings
5. ปรับ notification preference แล้วบันทึก

**ปัญหา/edge case:** ถ้าไม่พบ pattern ที่มีหลักฐานเพียงพอ ระบบต้องบอกว่ายังสรุปไม่ได้และไม่สร้างคำแนะนำแบบสุ่ม

**ผลลัพธ์ที่คาดหวัง:** ต้นเชื่อถือระบบมากขึ้นเพราะตรวจสอบคำแนะนำได้ และควบคุม notification กับข้อมูลของตนเองได้

## SC-P01 — ปุ๊กบันทึกคืนที่ทำงานดึก

**Persona:** ปุ๊ก — Sleep-Challenged User<br>
**Objective:** บันทึกข้อมูลการนอนและปัจจัยของคืนที่ผ่านมาได้อย่างรวดเร็ว

หลังประชุมข้าม time zone ปุ๊กตื่นมาแล้วรู้สึกเพลีย เธอเปิดหน้า sleep log และกรอกเวลาเข้านอน เวลาตื่น ระดับความรู้สึกหลังตื่น และเลือก tags ว่ามีความเครียดกับ screen time ก่อนนอน ระบบตรวจว่าข้อมูลครบและบันทึก record ให้เธอโดยไม่ต้องคำนวณเวลานอนเอง

**Action sequence:**

1. เปิด sleep log ตอนเช้า
2. ระบุเวลาเข้านอนและเวลาตื่น
3. ให้ rating และเลือก mood/feeling
4. เลือกปัจจัย เช่น stress, caffeine หรือ screen time
5. ตรวจสรุปแล้วกดบันทึก

**ปัญหา/edge case:** เวลาเข้านอนอาจอยู่ก่อนเที่ยงคืนและเวลาตื่นอยู่วันถัดไป หรือปุ๊กลืมกรอกบางช่อง ระบบต้องแจ้ง field ที่ขาดและคำนวณข้ามวันได้

**ผลลัพธ์ที่คาดหวัง:** ปุ๊กบันทึกข้อมูลได้ภายในไม่กี่นาทีโดยไม่รู้สึกว่าการติดตามเป็นภาระเพิ่ม

## SC-P02 — ปุ๊กค้นหาสาเหตุของคะแนนต่ำ

**Persona:** ปุ๊ก<br>
**Objective:** เปลี่ยนข้อมูลการนอนให้เป็นคำอธิบายสาเหตุที่เข้าใจได้

หลังบันทึกข้อมูลหลายคืน ปุ๊กเห็นว่า score ต่ำในคืนที่มีการประชุมดึก เธอเปิดรายละเอียดและเลือกเปรียบเทียบคืนที่มี stress กับคืนที่ไม่มี stress ระบบแสดง trend และรายการข้อมูลที่ใช้ พร้อมอธิบายว่าผลลัพธ์เป็น pattern เบื้องต้น ไม่ใช่การวินิจฉัยทางการแพทย์

**Action sequence:**

1. เปิด weekly dashboard
2. เลือกวันที่ score ต่ำ
3. ดู sleep duration, feeling และ activity tags
4. เปรียบเทียบกลุ่ม stress กับคืนปกติ
5. เปิดคำอธิบายของ insight

**ปัญหา/edge case:** ถ้าข้อมูลของปุ๊กไม่ต่อเนื่องหรือมีเพียง 1–2 records ระบบต้องแจ้งว่าข้อมูลยังไม่พอแทนการระบุสาเหตุแน่ชัด

**ผลลัพธ์ที่คาดหวัง:** ปุ๊กเข้าใจปัจจัยที่ควรทดลองปรับและไม่ถูกทำให้กังวลจากข้อความที่เกินหลักฐาน

## SC-P03 — ปุ๊กได้รับคำแนะนำที่ไม่ทำให้รู้สึกผิด

**Persona:** ปุ๊ก<br>
**Objective:** ได้คำแนะนำสั้นและเฉพาะบุคคลที่ทำตามได้จริง

ระบบพบว่าปุ๊กใช้หน้าจอก่อนนอนหลายคืน แต่แทนที่จะแจ้งเตือนซ้ำ ระบบแนะนำการทดลองหนึ่งอย่าง เช่น ลด screen time ก่อนนอน 30 นาที และให้เธอเลือกทำตาม เลื่อน หรือปิดคำแนะนำ ปุ๊กอ่านเหตุผลและบันทึกว่าจะลองทำเป็นเวลา 3 คืน

**Action sequence:**

1. เปิด recommendation card
2. อ่านคำแนะนำและเหตุผลจากข้อมูลของตนเอง
3. เลือก “ลองทำ 3 คืน” หรือเลื่อนคำแนะนำ
4. ระบบบันทึก preference และไม่แจ้งเตือนซ้ำถี่เกินไป
5. หลังครบช่วงทดลอง ระบบแสดงผลเปรียบเทียบอย่างระมัดระวัง

**ปัญหา/edge case:** ปุ๊กอาจปิด notification หรือยังทำตามไม่ได้ ระบบต้องไม่ถือว่าเป็นความล้มเหลวและไม่ส่งข้อความตำหนิ

**ผลลัพธ์ที่คาดหวัง:** ปุ๊กได้ action ที่ชัดเจนและยังรู้สึกควบคุมการตัดสินใจของตนเองได้

## SC-P04 — ปุ๊กตรวจ pattern ที่ต่างกันระหว่างวันทำงานกับวันหยุด

**Persona:** ปุ๊ก<br>
**Objective:** เข้าใจความไม่สม่ำเสมอของเวลานอนโดยไม่สรุปเกินข้อมูล

ปุ๊กสังเกตว่าวันทำงานกับวันหยุดมีเวลาเข้านอนต่างกันมาก เธอเลือก filter weekday/weekend และพบว่าข้อมูลบางคืนไม่มีเวลาเข้านอน ระบบแยกคืนที่ incomplete ออกจากการคำนวณและแนะนำให้บันทึกต่ออีกระยะหนึ่งก่อนสรุป trend

**Action sequence:**

1. เปิด history และเลือก filter weekday/weekend
2. ตรวจจำนวน records ของแต่ละกลุ่ม
3. เปิดคืนที่ข้อมูลไม่ครบ
4. แก้ไขหรือเติมข้อมูลถ้าจำได้
5. ดูคำแนะนำเรื่องความสม่ำเสมอของเวลานอน

**ปัญหา/edge case:** ถ้าข้อมูลไม่ครบหรือเวลาถูกกรอกผิด ระบบต้องให้แก้ไขได้และไม่ใช้ record นั้นสร้าง insight จนกว่าจะ valid

**ผลลัพธ์ที่คาดหวัง:** ปุ๊กเห็นความแตกต่างของรูปแบบชีวิตจริงและได้แนวทางปรับพฤติกรรมโดยไม่ถูกตัดสิน
